# /review — 작업 검토

방금 한 작업을 **다섯 축**으로 훑고, 근거(`파일:줄`)와 함께 심각도별로 보고한다.
기본은 **보고만** 한다 — 고치는 것은 사용자 확인을 받고 나서다(`--fix` 면 확인 없이 바로 수정).

> ⚠️ 없는 문제를 만들어내지 말 것. 깨끗하면 "문제 없음"이라고 분명히 말하는 것이 이 스킬의 정상 결과다.
> 지적은 **재현 시나리오나 코드 근거가 있을 때만** 한다. 추측이면 `확인 필요`로 표시하고 심각도를 낮춘다.

## 0. 검토 범위 정하기

| 인자 | 대상 |
|------|------|
| (없음) | 미커밋 변경이 있으면 그것, 없으면 마지막 커밋(`git show HEAD`) |
| `HEAD~3..` · 해시 | 그 커밋 범위 |
| 경로 | 그 파일/폴더 |
| `--fix` | 위 판정 그대로 + 발견 사항을 바로 수정 |

```bash
git status --short && git diff HEAD --stat
```
- ⚠️ **새로 만든 파일은 `git diff` 에 안 잡힌다** — `git status --short` 의 `??` 항목을 직접 읽는다. 신규 파일이야말로 가장 검토가 필요한 코드다.
- ⚠️ **이 리포는 Claude 세션을 여러 개 동시에 돌린다** — diff 에 이번 대화에서 만지지 않은 파일이 섞여 있으면 그것부터 사용자에게 알리고, 검토 대상에 넣을지 확인한다.

## 1. 어울림 — 이 코드가 이 프로젝트 것처럼 보이는가

- **배치**: 기능 코드가 `features/<기능>/` 안에 있는가. 공용이어야 할 것이 기능 안에, 기능 전용이어야 할 것이 `lib/`·`components/` 에 잘못 놓이지 않았는가.
- **경계**: 기능 간 참조는 `features/<기능>/index.ts` 공개 API 로만 하는가 (내부 파일 직접 import 금지).
- **컨텍스트 분리**: 렌더러에서 Node API 를 쓰지 않는가. 렌더러↔메인은 `window.oneApp`(preload) 경유인가.
- **공용 것을 썼는가**: `renderer/components/`(Button·Modal·Select·DatePicker·Checkbox … 네이티브 `input[type=date]`·`<select>`·원시 체크박스 금지) · `renderer/lib/`(usePolling·useCopy·usePopover·errMsg …) · `main/lib/`(fetchWithTimeout·store·broadcast·util). **전역 `fetch` 직접 사용 금지.**
- **스타일**: `_base.scss` 토큰(`var(--*)`)·타이포 믹스인만 썼는가. hex·px 매직넘버, `.btn`/`.input` 직접 사용, 기능 SCSS 에서 공용 클래스 크기 오버라이드가 없는가.
- **결**: 주석·문구가 한국어인가. 주변 파일의 네이밍·구조·주석 밀도와 톤이 맞는가.
- 세부 함정은 대상 파일을 열면 자동 로드되는 `.claude/rules/*` 를 따른다.

## 2. 이슈 — 동작이 틀릴 여지

- **실패 경로**: 에러가 잡히는가. 표시 문구는 `errMsg(e, fallback)` 인가(`(e as Error).message` 금지). IPC 는 `{ ok, error }` 를 확인하는가. **로딩·낙관 상태가 실패/늦은 응답에도 반드시 풀리는가**(이 앱에서 반복된 버그다).
- **비동기**: 경합(늦게 온 응답이 최신 상태를 덮음), 언마운트 뒤 setState, 중복 실행 가드, 취소 처리.
- **훅**: `exhaustive-deps` 경고를 남기지 않았는가. `usePolling`/`useTick` 에 **인라인 화살표를 넘기지 않았는가**(폴링 폭주 또는 미발화). effect 정리 함수에서 리스너·인터벌·구독을 해제하는가.
- **경계값**: 빈 배열·null·미로그인·긴 문자열·0건 응답에서 화면이 깨지지 않는가.
- **자원**: 자식 프로세스·pty·BrowserWindow·워처가 닫히는 경로가 있는가(과거 fd 누수 이력 있음).
- **보안**: 파일 경로를 클라이언트가 직접 넘기지 않는가(`handleShared` 는 식별자만 받고 저장소 밖 탈출을 검증). 외부 HTML 은 `sanitizeHtml` 을 거치는가. 비밀번호·토큰이 코드·로그·커밋에 남지 않았는가.
- **저장 위치**: 보존해야 할 데이터를 `localStorage` 에 두지 않았는가(강제 종료 시 유실 — IPC 로 userData JSON 에 저장).

## 3. 사이드이펙트 — 손댄 것이 딴 데를 건드리는가

**이 축은 반드시 `grep` 으로 확인한다.** 눈으로 diff 만 봐서는 절대 안 보인다.

바꾼 함수·타입·상수·CSS 클래스 이름을 뽑아 호출처를 전부 센다.
```bash
grep -rn "<바꾼이름>" src standalone --include=*.ts --include=*.tsx --include=*.scss
```

특히 아래 연결이 **끊기지 않았는지** 확인한다.
```
바꾼 것                    → 같이 봐야 할 곳
src/shared/types.ts        → main · preload · renderer 세 곳 전부
IPC 채널 추가·시그니처 변경 → main 등록(register*Ipc) · preload 노출 · shared 타입 ← 하나만 빠져도 런타임에서만 터진다
handleShared 로 등록        → 폰(MO)에 열리는 채널이다. 노출해도 되는 범위인가
broadcast 이벤트           → 모든 수신처(창이 여러 개다: 메인·팝아웃 터미널·MO)
renderer/components/* 수정  → 그 컴포넌트를 쓰는 모든 화면 ← 파급이 가장 크다
styles/_base.scss · 공통 클래스 → 앱 전체 + mobile-app 셸
approval 셀렉터·판정 로직   → standalone/overtime/ 복사본도 함께 고쳐야 한다
renderer/features/* 재사용  → mobile-app 이 렌더러를 재사용한다. 폰 화면에서도 성립하는가
```
- 상태를 여러 창이 공유하는 기능이면, **한 창에서 바꾼 값이 다른 창에 반영되는가**를 함께 본다.
- 시그니처를 바꿨는데 호출처가 1곳뿐이라 넘어갔다면, 그 사실을 근거로 적는다(확인했음을 남긴다).

## 4. 공통화 — 뺄 것 / 이미 있는 것

- **이미 있는 걸 다시 만들었나**: 새로 정의한 헬퍼·훅·컴포넌트가 있으면 `renderer/lib`·`renderer/components`·`main/lib`·`shared` 에 같은 것이 있는지 grep 으로 먼저 확인한다. 있으면 교체를 제안한다.
- **이번에 중복이 생겼나**: 같은 로직이 diff 안에서 2곳 이상 반복되면 후보로 올린다.
- ⚠️ **성급한 추상화는 지적하지 않는다** — 2회는 "후보", **3회부터 추출을 권한다**. 기능 간 결합을 새로 만들면서까지 빼는 것은 제안하지 않는다(빼야 한다면 `shared` 나 공용 `lib` 로 올리는 형태여야 한다).
- 반대로 **과한 추상화**(호출처 1곳뿐인 래퍼, 인자만 늘어난 옵션 객체)도 지적 대상이다.

## 5. 검증

```bash
npx tsc --noEmit        # 필수
npm run lint            # 훅 규칙 포함 — 경고 0 을 유지한다
npm test                # 순수 로직을 건드렸을 때
```
- 실행 확인이 필요하면 **개발 인스턴스(`npm start`)** 에서 본다. **빌드(`/build`·`npm run package`)는 사용자가 명시적으로 요청했을 때만.**
- 검토 중 새로 알아낸 함정은 `.claude/rules/` 의 해당 파일에 기록할지 제안한다(CLAUDE.md 아님).

## 6. 보고 형식

축 순서가 아니라 **심각도 순서**로 묶어서 낸다.

```
🔴 반드시 수정 — 동작이 틀리거나 다른 기능을 깨뜨림
🟡 검토 권장 — 컨벤션 이탈·잠재 위험·확인 필요
🟢 개선 제안 — 중복 정리·가독성 (안 해도 무방)
```
각 항목은 **한 줄 요약 → `파일:줄` → 왜 문제인지 → 어떻게 고칠지** 순으로, 짧게.
마지막에 **✅ 확인했고 문제 없던 것**을 한두 줄로 적는다(호출처 N곳 확인·tsc 통과 등) — 검토 범위를 사용자가 알 수 있어야 한다.

## 7. 수정

- 기본: 보고 후 `AskUserQuestion` 으로 **무엇을 고칠지** 묻는다(🔴 전부 / 🔴+🟡 / 선택 / 고치지 않음).
- `--fix`: 묻지 않고 🔴 → 🟡 순으로 수정하고, 끝나면 `npx tsc --noEmit` 을 다시 돌린 뒤 무엇을 고쳤는지 보고한다.
- **커밋하지 않는다.** 커밋은 사용자가 `/commit` 으로 지시할 때만.
